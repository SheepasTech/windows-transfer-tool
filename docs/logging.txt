DEBUG LOGGING
=============

Debug logging is always on. It cannot be switched off, on the old PC or the new PC.

Where the logs are
------------------
  %TEMP%\Debug\WindowsTransferTool\<yyyy-MM-dd>\<file>
  (usually C:\Users\<you>\AppData\Local\Temp\Debug\WindowsTransferTool\2026-10-15\debug-source-....log)
  One folder per day, one new file per run.

What is written there
---------------------
  debug-source-<yyyy-MM-dd_HH-mm-ss>.log        full console transcript of an old-PC run
  debug-destination-<yyyy-MM-dd_HH-mm-ss>.log   full console transcript of a new-PC run
  robocopy-<yyyy-MM-dd_HH-mm-ss>.log            robocopy's own log (new PC)
  Example: debug-destination-2026-10-15_14-30-05.log

The transcript is started by Start-DebugLog in Migrate-Windows.ps1 as soon as the
tool knows whether this is the old or the new PC. It is stopped when the tool ends,
including after an error. Every run makes a new file; old files are never overwritten.

Not in the temp folder
----------------------
  - With -Transport Drive on the old PC, the robocopy log is also written to
    WTT-Transfer\logs on the drive.
  - Registry backups and the installed-apps CSV on the new PC stay in
    %USERPROFILE%\Migration. They are reports, not debug logs.

Desktop shortcut
----------------
At the start of each run the tool looks for the shortcut
  Desktop\Debug.lnk
It opens %TEMP%\Debug, the whole debug folder, so every project and day is reachable.
  - If it exists, nothing happens.
  - If it is missing, the tool asks: Put a "Debug" shortcut (to the log folder) on the desktop? (Y/n)
    Enter creates it. n skips it (it asks again next run).
  - With -Yes, or when the tool is not interactive, it creates the shortcut without asking.
  - If the shortcut cannot be created, the tool prints a warning with the folder path.

The bootstrap (bootstrap.ps1) prints "Running: Migrate-Windows.ps1 -Mode ..." with the
exact parameters it passes to the tool. That line is part of the transcript.

Privacy: secrets are hashed in the saved log
--------------------------------------------
The old PC prints one-time sign-in details on screen for you to type on the new PC
(pairing code, FTPS/FTP password, SMB temporary-account password). The screen still shows
them in full. When the tool ends, it rewrites the saved debug log and replaces each of
those values with a short SHA-256 hash, for example:

  Pairing code:   [sha256:4981aa0a50d5]

So a log you keep or share does not hold a usable password. The hash lets you check that
two lines refer to the same value, nothing more. A short value such as a 6-digit code
could be guessed from its hash, but it stops working when the old PC finishes.

Limits:
  - The rewrite happens when the tool exits. If the window is killed or the PC loses
    power during a run, the log in the folder still holds the plain values. Delete it.
  - Only values the tool itself prints as secrets are hashed. Do not paste other
    sensitive data into the console during a run.
  - Saved Wi-Fi passwords are written to files in the export package, never printed, so
    they are not in the log.

Each window logs for itself
---------------------------
The bootstrap starts a second, elevated window (UAC) and exits in the first one. Every
window writes its own file, so a crash or a closed window never takes the earlier log with it:

  bootstrap-user-pid<N>-<yyyy-MM-dd_HH-mm-ss>.log    first (non-elevated) window
  bootstrap-admin-pid<N>-<yyyy-MM-dd_HH-mm-ss>.log   elevated window
  debug-<source|destination>-<yyyy-MM-dd_HH-mm-ss>.log   the tool itself (transcript)

The bootstrap log is appended one line at a time (role, transport, dry-run answer, each
download, the exact launch parameters, and any error with its stack trace), so it is on
disk even if the process dies. If the bootstrap fails it prints "Details: <path>".
If the tool itself fails, it writes "FAILED: <message>", the line and the stack trace into
its transcript before the window can close, then stops as before. All of this is wrapped
in try/catch; if the log folder cannot be written, the tool still runs and only warns.

Convention for other tools (e.g. the Office install tool)
---------------------------------------------------------
Use the same layout so one shortcut finds everything:
  Log files:  %TEMP%\Debug\<ProjectName>\<yyyy-MM-dd>\<kind>-<yyyy-MM-dd_HH-mm-ss>.log
  Shortcut:   Desktop\Debug.lnk  ->  %TEMP%\Debug   (shared by all projects; ask before creating)
  One file per process/window; elevated and nested windows write their own files.
  Append line by line, or use a transcript, so a crash keeps what was written.
  Hash any secret that is printed (see the privacy section above).
  Never let logging stop the tool: wrap every log call in try/catch.

winget app installs (new PC)
----------------------------
The "Reinstall apps with winget" item no longer runs one `winget import` for everything.
It reads apps.json and starts one separate, hidden winget process per app:
  - up to 3 run at the same time (Install-WingetApps -Parallel);
  - each app has its own log: <log folder>\winget\<app id>-<yyyy-MM-dd_HH-mm-ss>.log
    (plus a .err file with its error output);
  - an app that exits with an error, cannot start, or runs longer than 30 minutes
    (it is killed) is recorded and the others carry on;
  - failed apps are retried once, one at a time (parallel installs can collide on the
    Windows Installer lock);
  - the final report lists the apps that still failed and where their logs are.
Exit code 0 and 0x8A15002B (already installed) count as success.
